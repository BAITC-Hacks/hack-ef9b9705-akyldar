# План AI-модуля

Первоначальный план для изолированной рабочей папки: самостоятельный минимальный Go-модуль `hackalem/ai` в `ai/`, зависимости — стандартная библиотека Go. При передаче в командный репозиторий AI добавляется отдельной веткой от `main` (`051f110`); корневые настройки не меняются. Код отдельной ветки `origin/backend` (`ba61fef`) уже содержит router, модели, storage и rating. Он изучен для [инструкции интеграции](docs/integration.md), но в эту AI-ветку не перенесён; совместный flow не проверен.

## Контракт и flow

```text
Frontend → POST /api/ai/questions → проверка ввода → AI provider → проверка ответа
                                              ↘ ограниченный retry → fallback
Бизнес отвечает → POST /api/ai/card → тот же путь → редактируемая карточка
Человек проверяет и подтверждает → backend сохраняет и считает rating → публикация
```

API выполняется только на сервере. Вход передаётся отдельным JSON-сообщением, никогда не включается в system prompt. Ответы сохраняют установленную форму; режим передаётся заголовком `X-AI-Mode: live | fallback`. Ошибочный ввод возвращает 4xx, а не fallback. Для cross-origin frontend нужно открыть этот заголовок через `Access-Control-Expose-Headers`.

В задании сказано «12 полей», но явно перечислены **11**. Рабочий контракт использует ровно перечисленные 11 ключей; дополнительное поле не выдумывается. Если требуется двенадцатое поле, его имя и смысл согласуются отдельно до изменения контракта. `score` не входит в AI-ответ.

## Prompts и schemas до реализации

- `prompts/questions.txt`: 3–5 коротких уникальных вопросов на русском или казахском, опора на пропущенные сведения и неоднозначности, без неподтверждённых предпосылок.
- `prompts/card.txt`: только сведения из `description` и ответов пользователя; все 11 строк обязательны; неизвестное — `""`; вопросы не являются фактами; явное исправление имеет приоритет, неразрешимый конфликт оставляет поле пустым.
- `schemas/questions.schema.json` и `schemas/card.schema.json`: строгие объекты, required keys, `additionalProperties: false`; количество вопросов 3–5; значения карточки — строки. Непустоту и дубликаты проверяет Go.
- Инструкции внутри пользовательских данных не выполняются. Модель не подтверждает и не публикует карточки, не рассчитывает rating.

Provider: OpenAI Responses API, нативный Structured Outputs через `text.format` с `type: "json_schema"`, `name`, `strict: true`, `schema`. Синтаксис и поддержка проверены по [официальной документации Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Рекомендуемая модель — `gpt-4.1-mini`, задаётся конфигурацией; возможности проверены по [странице модели](https://developers.openai.com/api/docs/models/gpt-4.1-mini). Наличие подписки в интерфейсе не подтверждает API-доступ.

## Валидация, ошибки и fallback

Вход: ровно один корректный JSON object, известные поля, непустой `description`, строковые значения, корректный массив `answers`, ограничения размера тела, текста и числа ответов. Выход: один JSON object без постороннего текста, без пропущенных/лишних ключей, `null`, неверных типов и дубликатов ключей. Допускается снять одну полную внешнюю Markdown-обёртку; извлечение объекта из мусора и ремонт JSON запрещены.

Общий deadline по умолчанию 15 секунд, максимум две попытки провайдера с короткой отменяемой задержкой. Отсутствующий ключ и принудительный fallback не вызывают сеть. 401/403 не повторяются; отмена клиентом немедленно прекращает работу. Временные сетевые ошибки, 429/5xx и непригодный ответ допускают вторую попытку в пределах deadline; далее fallback. Ограничиваются размер внешнего ответа и входа, response body закрывается. Ключи и полный пользовательский текст не пишутся в обычные логи. Пустой ответ, отказ, обрезанный вывод, невалидные JSON/схема явно обрабатываются.

Questions fallback: локальные вопросы RU/KK, по возможности исключающие заполненные категории. Эвристики не заменяют понимание моделью и могут пропускать перефразированные факты. Card fallback: исходный `description` дословно в `context`, остальные поля пустые; заполнение вручную обязательно. Режим явно виден frontend.

Для исчерпывающего описания требования «минимум 3 вопроса» и «не повторять уже сообщённое/не выдумывать проблемы» могут быть несовместимы. Это ограничение контракта фиксируется в документации; нельзя изображать общие дополнительные вопросы как обнаруженные пробелы. Человек всегда проверяет результат.

## Проверки и примеры

- `httptest`/fake provider без ключа и интернета: валидные вопросы и карточка; 2/6/пустые/повторные вопросы; неверные типы, `null`, лишние/пропущенные ключи; повреждённый JSON, code fence, посторонний текст.
- Сетевой путь на локальном fake HTTP server: timeout/cancel, 401/403 без retry, 429/5xx с максимум двумя попытками, пустой ответ/refusal/truncation, ограничения размера.
- Ввод: пустой description, oversized body/text/answers, неизвестные поля и неверные типы. Проверка отсутствия ключа и forced fallback.
- Отдельные semantic evaluation cases: слабое и подробное описание; неизвестные бюджет/срок; «не знаю»; конфликт и явное исправление; prompt injection; RU/KK; отсутствие выдуманных чисел, контактов, технологий. Структурная проверка не доказывает смысловую достоверность; важные факты и числа требуют отдельных проверок и ручного контроля.
- `go test ./...`, `go vet ./...` и локальная проверка двух endpoints. Реальные команды и результаты фиксируются после выполнения. Live evaluations выделяются отдельно и без credentials не объявляются выполненными.

## Интеграция и передача

Небольшой заменяемый provider interface → service → HTTP handlers. Конфигурация читает переменные процесса; `.env` автоматически не загружается. Backend подключает два handler к существующему router; при переносе согласует импорт/расположение пакета. Frontend показывает `X-AI-Mode`, редактирует карточку и требует подтверждения человеком.

Первоначально rating в изолированной папке отсутствовал. При передаче изучен `rating.Calculate` в `origin/backend` (`ba61fef`): `context`/`need` по 10, `contact`/`interaction_format` по 5, остальные веса соответствуют заданию; заполненность — непустой текст после trim. AI не реализует вторую формулу. Обработку «не знаю» и сохранение ответов следует согласовать при интеграции; численные результаты совместного flow пока не проверены.

Документация отделяет проверку AI-стенда от интеграции сохранения, rating, каталога, публикации и принятия proposal из других веток. Общий end-to-end flow остаётся `not tested` до объединения и проверки компонентов. Demo на 2–3 минуты начинается с «Хотим автоматизировать работу склада», раскрывает факты постепенно и явно показывает fallback.
