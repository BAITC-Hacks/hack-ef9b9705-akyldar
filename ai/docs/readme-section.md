## Проблема и решение

Бизнес часто описывает задачу слишком кратко, чтобы студенческая команда могла оценить объём работы. AI-модуль задаёт уточняющие вопросы, затем преобразует описание и ответы в структурированную Task Card. Человек редактирует и подтверждает результат. Неизвестные сведения остаются пустыми; модель не должна придумывать бюджет, сроки, технологии или критерии успеха.

## Реализованная функциональность

В `ai/` расположен самостоятельный Go-стенд для интеграции: два HTTP endpoints, серверный OpenAI provider, отдельные prompts, строгие JSON schemas, локальная валидация, ограниченные retries и явный fallback. Поддерживаются русский и казахский ввод. Есть offline-тесты, synthetic fixtures, semantic evaluation cases и demo-сценарий.

Сохранение задач, rating, подтверждение, публикация, каталог и proposals не входят в этот стенд. Их доступность и интеграционные статусы описываются отдельно по фактической реализации приложения.

## Основной flow

Бизнес описывает задачу → AI задаёт 3–5 вопросов → бизнес отвечает → AI формирует черновик карточки → человек проверяет/редактирует/подтверждает. Следующие этапы целевой платформы: backend сохраняет карточку и считает rating, бизнес публикует задачу, команда отправляет предложение, бизнес принимает его. Эти последние этапы требуют соответствующих компонентов платформы.

## Архитектура и технологии

Go 1.22+, стандартная библиотека: HTTP handlers → validation → service → provider. Сервер вызывает OpenAI Responses API; frontend никогда не получает API key. Prompts и schemas подключаются к модулю как локальные ресурсы. Модель задаётся через окружение; рекомендуемое начальное значение — `gpt-4.1-mini`, согласно [официальной странице модели](https://developers.openai.com/api/docs/models/gpt-4.1-mini).

## AI integration и prompt design

Для questions и card используются разные system prompts. Пользовательский текст передаётся отдельным JSON, рассматривается как недоверенные данные и не меняет системные правила. Responses API получает нативную JSON Schema с `strict: true` через `text.format`; синтаксис проверен по [официальной документации Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Карточка использует только `description` и пользовательские `answer`. Сам текст вопроса не подтверждает факты. Явные исправления учитываются; неразрешимый конфликт оставляет затронутое поле пустым. Результат и критерии успеха разделены: «нужен чат-бот» не означает «точность 80%».

## Input/output

| Endpoint | Input | Output |
|---|---|---|
| `POST /api/ai/questions` | `{description: string}` | `{questions: string[]}`, 3–5 вопросов |
| `POST /api/ai/card` | `{description: string, answers: [{question: string, answer: string}]}` | Карточка с 11 обязательными string-полями |

Поля карточки: `title`, `context`, `need`, `users`, `data`, `constraints`, `expected_result`, `success_criteria`, `contact`, `interaction_format`, `topic`. Неизвестное — `""`; дополнительных ключей, `null` и `score` нет. В исходном задании названы «12 полей», но перечислено 11; реализован перечисленный набор.

Успешный ответ содержит заголовок `X-AI-Mode: live | fallback`. Fallback карточки сохраняет исходное описание только в `context`, остальные поля пустые для ручного ввода. Ошибочный пользовательский ввод получает 4xx. [Контракты и статусы](ai/docs/integration.md).

## No-invention и ограничения

Консервативный prompt, schema validation и эвристические проверки чисел/контактов/URL/известных технологий снижают риск недостоверных добавлений. Они не гарантируют смысловую истинность. Нужны отдельные live evaluations и проверка человеком. Fake-provider tests проверяют код на заданных ответах, а не качество настоящей модели.

Локальные fallback-вопросы определяют язык и заполненные категории приближённо. Для полностью исчерпывающего описания минимум 3 вопроса может конфликтовать с запретом повторять сообщённое. Карточка всегда остаётся черновиком до человеческого подтверждения.

## Rating

AI не возвращает и не рассчитывает score. В просмотренной `origin/backend` (`ba61fef`) есть `rating.Calculate`: Context + need — 10 + 10 независимо, Data — 20, Expected result — 15, Success criteria — 15, Constraints — 10, Users — 10, contact + interaction_format — 5 + 5. Непустой после trim текст считается заполнением, включая «не знаю». Совместное сохранение карточки и расчёт rating с AI не проверены; численные результаты demo требуют фактического вызова backend.

## Установка, env и запуск

Нужен установленный Go 1.22+ в PATH (для просмотренного backend — 1.25+). У AI-модуля нет внешних Go dependencies. `.env` и portable tools не входят в клон. Для live создайте локальный `ai/.env` из `ai/.env.example` по [README](ai/README.md); сервер читает `OPENAI_API_KEY`, `OPENAI_MODEL`, `AI_TIMEOUT_SECONDS=15`, `AI_MAX_ATTEMPTS=2`, `AI_FORCE_FALLBACK=false` из окружения процесса. Windows launcher `.\ai\run.ps1` загружает локальный `.env`, исключённый из Git; прямой `go run` файл не читает. Для live ключ передаётся только серверу; рекомендуемая модель — `gpt-4.1-mini`.

PowerShell, запуск без ключа:

```powershell
Set-Location .\ai
$env:AI_FORCE_FALLBACK = 'true'
go run ./cmd/demo
```

Сервер слушает `http://127.0.0.1:8080`. [README AI-модуля](ai/README.md) содержит работающие UTF-8 PowerShell-примеры для обоих endpoints и переключение live/fallback.

## Проверка жюри

```powershell
Set-Location .\ai
go test ./...
go vet ./...
```

Offline-проверки используют fake provider и локальный HTTP server, не требуют API key или интернета. Фактические результаты запуска и статусы live/end-to-end следует смотреть в [checklist](ai/docs/integration-checklist.md). Live-проверка требует отдельного API-доступа. При недоступности API жюри показывается явный fallback, а не заранее записанный ответ под видом AI.

Сценарий на 2–3 минуты начинается с «Хотим автоматизировать работу склада»: [demo](ai/docs/demo.md). Полные численные rating показываются только после подключения реальной согласованной формулы.

## Synthetic data и передача

В [testdata](ai/testdata/) — 5 drafts разной полноты, 5 полных карточек с исходными description/answers, 5 команд и 5 proposals. Темы: logistics, education, retail, healthcare administration, analytics. Данные synthetic, ссылки `example.com` демонстрационные, реальные чувствительные данные не используются. Task/team IDs согласованы через fixture envelopes; AI schema не содержит служебных IDs.

Backend подключает handlers, env, CORS metadata при необходимости и человеческое подтверждение по [инструкции интеграции](ai/docs/integration.md). Остальная платформа, live AI и end-to-end имеют отдельные статусы; нельзя считать их проверенными на основании unit tests AI-модуля.
